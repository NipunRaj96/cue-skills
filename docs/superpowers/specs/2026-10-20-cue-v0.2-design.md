# Cue v0.2 design: automatic picker and drift enforcer

## Intent

Nipun collects skills from GitHub (graphify, headroom, caveman, ponytail, superpowers, frontend-design and many more). In daily work two things go wrong:

1. **Situational skills never fire.** Example: he was replicating a Stitch design in frontend code. `frontend-design` and the other design skills were installed but never used, because he forgot they existed. With hundreds of skills, nobody knows which one fits.
2. **Standing skills fade.** caveman (terse output) and ponytail (minimal code) stop being followed partway through a session, so he has to repeat them again and again. Even with caveman's own hook reminding the agent on every prompt, the agent still drifted. Injection alone does not make the agent comply.

v0.1 is a rules engine, so the user must still know and write which skill fits. v0.2 delivers the original idea: **the right skill at the right moment, with no human intervention, and with no setup beyond install.**

## Success, as Nipun defined it

- **Token usage drops a lot.**
- **Output gets better without him naming a skill.**

## Goals

1. **Picker.** Choose situational skills automatically from what is happening, using four signals:
   - the prompt text;
   - the tool calls, including MCP tool names such as `mcp__stitch__*`;
   - the files read or edited;
   - the project markers, such as `package.json` dependencies.
2. **Enforcer.** Detect when a standing skill is no longer being followed, and correct it on the next turn.
3. **Zero config.** `npm i -g cue-skills && cue-skills init` is the whole setup. No rules file is needed. New skills are indexed automatically.
4. **Visible.** Whenever Cue acts, show one line, for example `cue → frontend-design (design task)` or `cue → caveman re-applied (drift)`.
5. **Proof.** An offline picker-accuracy eval that needs no LLM, against the real skills installed on this machine.

## Non-goals for v0.2

- **An LLM-based picker or a cloud service.** Everything stays local and free.
- **A compliance checker for every possible skill.** Only skills that are measurable get one; the rest rely on re-injection.
- **Forcing a rewrite with a blocking Stop hook.** That spends tokens, which works against the goal. Correction happens on the next turn.
- **LLM-judged quality benchmarks.** These are deferred until model quota is back.

## Anti-goals

These count as failure even if everything else works:

- **Noise.** Injecting skills on most prompts for no reason. A wrong pick costs tokens and trust.
- **Friction.** Any required config, any prompt that blocks the user, any maintenance step.
- **Slowness.** A hook that takes more than about 150 ms when the catalog cache is warm.
- **Pretending.** Claims in the README that the eval has not shown.

## Decisions Nipun made

- **When unsure, offer more than one.** When two or three skills are close, show them all as a short shortlist, and the agent picks. The user should never have to research skills.
- **Visible by default.** The one-line notice tells people that something is helping in their session.
- **Frictionless above all.** Easy to set up, use and maintain, and genuinely useful day to day.

## How it works

### Skill cards (built into the catalog)

Each skill gets a card with these fields:
- `name`, `description`, and `when_to_use` from the frontmatter where present;
- `path` and `plugin`;
- `tokens`, the estimated size of the body;
- `invocable_only`, from `disable-model-invocation: true`. These skills are never auto-picked.

Duplicates, meaning the same skill installed from several plugins or versions, are collapsed. User skills win over plugin skills.

### Signals become a query

- **Prompt:** the text from UserPromptSubmit and its equivalents.
- **Tools:** the tool name and file path from PreToolUse and its equivalents. A small built-in expansion table maps strong signals to words:
  - `.tsx`, `.jsx`, `.css`, `.html`, `.vue`, `.svelte` → "frontend ui design component";
  - `mcp__stitch__*`, `figma` → "design ui replicate";
  - `test` files or test failures → "testing debug";
  - and similar entries.
- **Project:** a one-time per-session summary of `package.json` dependencies (react, next, tailwind and so on) and the main languages.

### Scoring

- BM25 over the card text (name weighted ×3, then description and when_to_use), using the signal query. Plain JS, no dependencies.
- The design keeps a seam for an optional local embedding re-ranker (Ollama `nomic-embed-text`). The eval decides whether it is worth shipping.

### Decision

| Outcome | Condition | Action |
|---|---|---|
| Confident | top score ≥ `hi` and ≥ `margin` × the second score | inject the full skill body |
| Close call | top scores ≥ `lo` | inject a **shortlist** of up to 3 cards (name, one-line purpose, path) under the line "Relevant skills; read the file of the one that fits." |
| Nothing | otherwise | inject nothing |

- `hi`, `lo` and `margin` are tuned on the eval set and shipped as defaults.
- A skill already injected in the session is not injected again unless compaction happens.
- Standing skills are never candidates.

### Standing skills and the enforcer

- **Standing skills** are the user's pinned always-on skills. `init` offers to pin well-known ones it finds installed (caveman, ponytail and similar) with a single yes/no question.
- **Compliance checkers** are small pure functions per skill:
  - `caveman`: filler-word and article ratio, plus reply length compared with the session median.
  - Skills without a checker get a periodic re-injection: the full body every N turns, plus the one-line reminder on every turn.
- **Observe:** after each reply, read the last assistant message and score it.
  - Claude Code: the `Stop` hook, with `transcript_path`.
  - OpenCode: `message.updated` and `session.idle`.
  - Antigravity: `PostInvocation`.
  - OpenClaw: `agent_end`.
  - Gemini: `AfterAgent`.
- **Correct:** on a failed score, set a drift flag in the session state. On the next prompt, inject the full skill body again with a factual note ("Previous reply did not follow caveman: N filler words."), and show the visible line.

### Visibility

- Claude Code shows `systemMessage` in the UI. It costs zero model tokens.
- Agents without a user-visible channel are asked to begin their reply with `cue → …`, which costs about 10 tokens.
- `quiet: true` in the optional rules file turns it off.

### Zero-config setup

`init` runs these steps:
1. Detect the agents and install their adapters.
2. Index the skills.
3. Ask one question: "Pin these always-on skills? caveman, ponytail [Y/n]".
4. Write `~/.cue/rules.yaml` only if the user pins something.

Rules stay as optional overrides. `when` rules still force a skill, and `never` still blocks one.

## Proof: the offline eval

The eval lives in `bench/picker/`:
- **Cases:** 100+ labeled cases. Each case has a prompt and/or tool events and files, the skills expected to fire, and skills that must not fire. The cases are written against the 99 skills actually installed here, and include Nipun's Stitch-to-frontend case.
- **Metrics:**
  - top-1 accuracy;
  - shortlist hit rate (the expected skill is in what was injected);
  - false-fire rate on neutral prompts that should inject nothing;
  - injected tokens per case.
- **Context savings:** also report the token cost of listing every skill description in context, compared with Cue's injections.
- **Rules:** the eval runs in `npm test` with a minimum threshold, so a regression fails CI. The thresholds come from the first honest run.

The token and quality benchmarks (`bench/run.js`, plus the drift suite) run again when model quota returns. They are not used as headlines until then.

## Scope and settled decisions (2026-10-20)

**Agents (Nipun's decision)**
- **Claude Code** gets everything: picker, enforcer and visible line. It is live-tested in the Claude desktop app's Code sessions, because that is the only model quota available.
- **OpenCode and Antigravity** get the picker and enforcer as best effort, with unit tests only and no live test until quota returns.
- **Codex, Cursor, Gemini and OpenClaw** keep the v0.1 behaviour.

**Token cap (Nipun's decision)**
- Injected skill text is capped at about 2,000 tokens per turn.
- A skill whose body is over about 1,500 tokens is injected as a card plus `Read <path>`, even when the picker is confident.
- Smaller skills are injected in full.

**Builder-check calls (the controller's calls; Nipun may override)**
- **Tool signals.** Claude PreToolUse matcher: `Read|Edit|Write|MultiEdit|mcp__.*`. Claude PostToolUse on `Bash` is used only to detect test failures (a non-zero exit plus test-runner output). There is no all-tools matcher.
- **Queries.**
  - Each event is scored on its own: the prompt hook uses the prompt; a tool hook uses that tool's signal.
  - The project summary is appended to the first query of a session only.
  - A pick made off a tool event counts as injected.
- **State.**
  - A shortlist counts as injected for every skill on it.
  - Compaction or `clear` resets the state.
  - A subagent gets the standing skills plus the current picks, without tracking state.
- **Visible line.** At most one line per turn; several events in one turn are merged into one line.
- **Drift defaults.**
  - The caveman thresholds come from the existing benchmark data (`bench/results`). They are recorded in code with a comment naming the data.
  - Skills with no checker get their full body re-injected every 10 turns.
  - ponytail gets periodic re-injection only.
- **Duplicates.**
  - Two entries are the same skill when they have the same `name`.
  - Precedence: user, then project (trusted), then plugin (newest version, then plugin name alphabetically).
  - `plugin:name` still selects exactly.
- **Eval data.**
  - The cards of the 99 installed skills (name, description, when_to_use, token estimate) are frozen into `bench/picker/cards.json`, so CI does not depend on this machine.
  - The controller writes the labeled cases, including the Stitch → frontend case.
  - Thresholds are tuned on 70% of the cases. Scores are reported on the held-out 30%.
- **`init` without a TTY.** It skips the pin question and pins nothing.

## Constraints

- Node 18 or later. The only runtime dependency is `yaml`. No network.
- All v0.1 security guarantees stay in place: project trust, safe reads, fail-open behaviour.
- Hook budget: under about 150 ms with a warm cache. BM25 runs over cached cards and precomputed term stats.
- Nipun Kumar is the sole author, with no AI attribution anywhere.
